# K-025 — Arranque integrado y distribución Ubuntu

Verificado el 2026-10-31 en Ubuntu 24.04 amd64. Paquete generado: `apps/desktop/src-tauri/target/release/bundle/deb/Konsora_0.1.0_amd64.deb` (19,99 MiB). Compilación con `npm run package:ubuntu`.

## Resultado

- Backend PyInstaller incluido como recurso; arranque privado desde Rust con puerto del SO, stdin autenticado, entorno sin credenciales heredadas y parada al cerrar la ventana. Comprobación adicional del binario empaquetado: EOF termina el servicio y libera su puerto, sin secretos en stdout/stderr.
- Instancia única mediante el plugin oficial `tauri-plugin-single-instance` 2.5.5, registrado primero. Segunda apertura enfoca la ventana existente y termina; el proceso principal conserva su servicio. Es la única nueva dependencia de escritorio de este bloque y evita mantener una implementación DBus propia.
- Registro en el directorio XDG de datos, 0700; base nueva y bloqueo 0600. Bloqueo exclusivo del registro durante el servicio/mantenimiento; un diagnóstico concurrente se rechaza. Directorios de datos enlazados rechazados.
- Importación explícita de SQLite sin sobrescribir: snapshot consistente, migraciones sobre la copia, clave de revisiones conservada y origen intacto. No lee ni escribe archivos de los proyectos durante la importación. Diagnóstico sin HTTP, secretos ni migraciones.

## Comprobaciones realizadas

1. Tres pruebas nuevas de mantenimiento correctas: copia de tablas adicionales/clave/origen, rechazo de destino existente, exclusión mutua, origen inválido y directorio enlazado. Tras ajustar el cierre de conexiones, se ejecutaron únicamente mantenimiento y seguridad afectados: 11 casos correctos. Las otras 98 pruebas de negocio y tres del tablero ya habían pasado en K-032; no se repitieron.
2. Build web con tipos y build nativo release correctos; `.deb` generado con icono, lanzador y backend. `apt-get -s install ./...deb` resuelve las dependencias del paquete en este Ubuntu sin cambios de sistema.
3. Instalación real del paquete mediante `dpkg --root` en `.tools/k025-install/root`, con su propia base de paquetes. Primera apertura con directorios XDG vacíos, usando **el ejecutable instalado**, sin crear previamente el registro ni arrancar una API: crear proyecto por teclado → selector de carpeta → detectar archivo externo → seleccionar A → preparar → copia exacta al portapapeles GTK. Trabajo no seleccionado excluido.
4. Durante ese recorrido, 8000 y 1420 ocupados por sockets propios de QA: arranque correcto en otro puerto. Segunda apertura sale correctamente, la primera sigue activa; mantenimiento simultáneo rechazado. Cierre normal de ventana termina padre/servicio y permite diagnóstico de integridad/permisos.
5. Reinstalación del mismo `.deb` con la aplicación cerrada, eliminación de la caché XDG de QA y reapertura: proyecto y tareas recuperados. Desinstalación con `dpkg --purge`: ejecutable eliminado, registro y `tasks.json` idénticos a los guardados antes de la actualización.
6. Importación usando **el backend instalado** desde una base con esquema 2: migración a esquema actual, chat/mensaje históricos y clave conservados; origen sin cambios; segundo intento de importación rechazado. Diagnóstico funciona incluso con PATH sin Python/Node. Destino enlazado rechazado.

La instalación usa una raíz aislada con las bibliotecas del host Ubuntu, por lo que `dpkg` fuerza dependencias en esa base aislada; la resolución normal se comprueba por separado con la simulación de apt. No se instaló el paquete con sudo en el sistema personal ni se probó una VM vacía u otra distribución/arquitectura. No hay scripts de paquete que eliminen datos de usuario. El escritorio virtual requiere adaptar foco/nombres accesibles en la automatización; los avisos de portales/PipeWire no impiden el flujo.
