# K-005A — Debates simulados persistentes

Fecha: 2026-10-30. Ubuntu 24.04, Python 3.12, SQLite, Node 22 y escritorio Tauri.

**Completada únicamente K-005A.** Se verifica el flujo proyecto → debate → dos propuestas simuladas independientes → persistencia y consulta. No se necesita Claude ni una cuenta; no se han ejecutado CLIs reales ni consumido cuotas en esta verificación. K-005B y K-005 siguen pendientes, y K-006 conserva su dependencia.

## Implementación

- Migración SQLite v3 transaccional: `debates` pertenece al proyecto y conserva problema, contexto, indicador de simulación y fechas. `proposals` guarda dos participantes ordenados A/B con UUID, nombre, conector/modelo, simulación, estado, texto/error y fechas de creación/inicio/fin. Las restricciones impiden estados incoherentes y las claves foráneas eliminan debates/propuestas al borrar el proyecto mediante su confirmación existente, actualizada para explicar el alcance.
- La migración conserva proyectos, conversaciones y mensajes anteriores. Los chats mantienen su contrato y funcionamiento. En el proyecto se añade navegación Conversaciones/Debate, con Conversaciones seleccionada inicialmente.
- El problema y el contexto se introducen expresamente y se fijan al crear el debate; no se leen chats, archivos u otros proyectos. Ambos simuladores reciben el mismo JSON serializado, sin propuestas ajenas. Cada uno produce una plantilla distinta, claramente marcada como ejemplo fijo y sin presentarse como una inferencia real.
- `DebateSimulator` implementa el contrato `AgentConnector`. El registro de participantes del debate es independiente del de CLIs reales y solo contiene los dos simuladores. El cliente no puede elegir conectores, modelos, comandos ni modo real; no existe fallback a Codex, Claude o una API.
- Se crean las dos propuestas pendientes atómicamente y se inicia la simulación en una acción posterior. Solo hay una propuesta inicial por participante; no hay rondas, síntesis ni tareas. Los estados son pendiente, en curso, completada, fallida o cancelada. Una ejecución iniciada no se reenvía ni se repite: para repetir se crea otro debate.
- Cada resultado se guarda en su propia transacción al terminar, sin una transacción abierta durante la simulación. La finalización comprueba la identidad y el tamaño de la respuesta. Un fallo individual se conserva como error controlado, sin diagnósticos originales; no elimina el otro resultado. Las escrituras de cancelación solo afectan a propuestas aún en curso, sin sobrescribir las completadas o fallidas.
- La UI muestra problema/contexto guardados, identidad y estado de ambos participantes, fechas, resultados y errores. Consulta el progreso mientras hay propuestas en curso, permite actualizar manualmente y cancelar, y conserva las propuestas terminadas. Representa todo como texto, sin interpretar HTML. Claude Code aparece como no disponible y el debate real está deshabilitado.

## Contrato HTTP

Todas las rutas están bajo `/projects/{project_id}/debates`. Reutilizan la comprobación de host/origen local y JSON para POST de K-003/K-004.

| Método | Ruta | Resultado |
| --- | --- | --- |
| GET | Raíz | Lista del proyecto por fecha de creación descendente e ID como desempate. |
| POST | Raíz | `{problem, context?}` → `{debate, proposals}`, HTTP 201; no inicia la simulación. |
| GET | `/{debate_id}` | Debate y sus dos propuestas por posición A/B. |
| POST | `/{debate_id}/run` | `{}` → inicia una única simulación y devuelve el historial al terminar. |

Los IDs ajenos o inexistentes devuelven 404; campos/IDs inválidos o adicionales, 422; ejecuciones repetidas o simultáneas del mismo debate, 409; fallo de SQLite, 503. Los errores de validación no reflejan el cuerpo enviado. No se admiten parámetros para activar participantes reales.

Límites: problema 1–16000 caracteres tras recortar extremos, contexto hasta 32000 y prompt JSON completo hasta 64000. Cada simulador tiene 5 segundos para responder y una salida máxima de 24000 caracteres. Se omiten formatos conocidos de credenciales antes de guardar entradas, crear el prompt o persistir resultados. No hay dependencias nuevas.

## Cancelación, reinicio y almacenamiento

Cancelar, cambiar de debate/sección/proyecto o cerrar la ventana aborta el POST. La desconexión ASGI cancela los trabajos de ambos participantes; los ya terminados conservan texto, identidad y fechas. Las propuestas que aún estaban en curso pasan a canceladas. No quedan trabajos en segundo plano ni se reanuda automáticamente el debate.

Después de un cierre inesperado del backend, la primera operación de Debate del nuevo servicio marca como canceladas las propuestas que seguían en curso. Mantiene los resultados terminados y los debates pendientes que nunca se iniciaron. La recuperación es transaccional, una vez por instancia y perezosa: un problema de SQLite no impide consultar `/health`.

Esta coordinación está diseñada para el backend local actual de **un solo proceso**. No se debe arrancar otro backend sobre la misma base mientras haya debates ejecutándose: una nueva instancia interpretaría esas propuestas como interrumpidas. La coordinación entre varios procesos y el ciclo de vida integrado corresponden a la estabilización y distribución; no se simula soporte que aún no existe.

La comprobación global de instalación/login de Codex de K-004 permanece sin cambios y no realiza inferencias. Las rutas de Debate no invocan ni siquiera esa comprobación; usan su registro separado de simuladores. En la verificación de UI también se sustituyó el indicador global por un conector local de QA para evitar toda invocación de CLI real.

La verificación manual automatizada usa una base aislada `.tools/k005a-1793365935398.sqlite3`, simuladores y conectores locales de QA:

- Crear un proyecto/chat, enviar al simulador y conservar su turno al cambiar a Debate.
- Crear un debate con contexto explícito y texto con etiquetas HTML; ejecutar y ver Simulado A/B completados, modelos/fechas y texto escapado.
- Cancelar el POST después de guardar A y mientras B espera: A conserva exactamente su contenido y fechas, B queda cancelada.
- Inyectar un fallo en B desde el servidor de QA: A permanece completada, B muestra un error controlado y un diagnóstico secreto ficticio no aparece en UI ni logs. No hay controles de fallos artificiales en el producto.
- Detener abruptamente el servidor de QA con A completada y B en curso; arrancarlo de nuevo sobre esa misma base y actualizar: A permanece intacta y B se marca como interrumpida/cancelada, sin reenvíos.
- Recargar y abrir el mismo proyecto: recuperar el chat previo y el debate inicial con problema, contexto, identidades, fechas y ambas propuestas idénticas. Otro proyecto abre una lista de debates vacía.
- Revisar visualmente 1100 × 850 y 640 × 640, sin desbordamientos horizontales, errores JavaScript, trazas de backend ni tráfico de la página fuera de loopback.
- Abrir el binario de producción en Ubuntu, entrar al proyecto y Debate, abrir las propuestas, leer el contexto y actualizar. Cambiar a Conversaciones y recuperar el turno anterior. Cerrar tanto API como escritorio y repetirlo correctamente. La introducción de texto y ejecución se comprobaron en Chrome; AT-SPI comprueba navegación, lectura, actualización y cierre nativos.

## Repetir manualmente

1. Iniciar API y escritorio como indica README; crear o abrir un proyecto y seleccionar Debate.
2. Introducir problema/contexto y crear el debate. Revisar la entrada guardada y los dos participantes pendientes; el modo real debe permanecer deshabilitado.
3. Iniciar la simulación, consultar ambas propuestas y comprobar que están marcadas como ejemplos simulados.
4. Crear otro debate, iniciarlo y cancelar después de que termine A y antes de que termine B. Actualizar y comprobar que A se conserva y B está cancelada.
5. Reiniciar API y escritorio y recuperar ambos debates y un chat anterior. Crear otro proyecto para comprobar el aislamiento.
