# K-004 — Conversaciones por proyecto

Fecha: 2026-10-29. Ubuntu 24.04, Python 3.12, Node 22, Codex CLI 0.165.0 con sesión de ChatGPT.

**Completada:** chats y mensajes persistentes, elección de conector/modelo e historial aislado por proyecto y conversación. Se ha continuado un chat real con Codex después de reiniciar API e interfaz. El escritorio nativo recupera el historial al cerrar y abrir de nuevo, también tras reiniciar la API.

## Implementación y decisiones

- Migración SQLite v2, transaccional: `conversations` pertenece a un proyecto y `messages` a una conversación. Las claves foráneas eliminan los chats y mensajes al borrar su proyecto con la confirmación existente, cuyo texto ahora explica ese alcance. Los proyectos de v1 se conservan.
- Los mensajes tienen posición única por conversación, rol, texto, fecha y conector/modelo. Se leen por posición, sin depender de que las fechas sean distintas. Cada respuesta conserva su modelo aunque cambie el siguiente turno.
- Cada turno se guarda en una sola transacción después de responder el conector: mensaje del usuario, respuesta y preferencias del chat. Ante fallo/cancelación no se guardan turnos parciales. Los turnos anteriores permanecen intactos y el borrador se conserva mientras se siga en ese chat.
- La UI permite nombrar/crear chats, abrirlos desde la lista del proyecto, consultar historial, escoger Simulado o Codex, elegir modelo en un desplegable y enviar/cancelar mensajes. Incluye carga, errores, actualización y etiquetas accesibles. Cambiar de chat o proyecto aborta la petición y descarta el borrador sin enviar.
- El desplegable obtiene el catálogo oficial mediante [`codex debug models`](https://learn.chatgpt.com/docs/cli/reference#codex-debug-models), sin inferencias ni listas fijas. Se filtran modelos ocultos, IDs/nombres inválidos y duplicados; solo se devuelven `{id, name}`, sin el resto de metadatos. Se mantiene la opción predeterminada y cualquier modelo previamente guardado aunque esté ausente del catálogo. El acceso se valida al enviar, no se deduce de su presencia en la lista.
- La selección se valida como identificador y se pasa como argumento separado mediante la opción oficial [`--model`](https://learn.chatgpt.com/docs/models). No se modifica el conector compartido. La opción predeterminada conserva el comportamiento de K-003: `KONSORA_CODEX_MODEL` o predeterminado del CLI. Las preferencias se guardan al completar el turno.
- Solo se serializan como texto los roles/contenidos del chat solicitado, más el nuevo mensaje. No se incluyen otros chats, proyectos ni archivos. Un límite de 64000 caracteres para el contexto serializado impide envíos sin acotar; si se supera, se pide abrir otro chat sin truncar ni resumir el historial. Cada mensaje nuevo mantiene el límite de 16000 caracteres.
- El simulador responde al último mensaje sin repetir todo el contexto. El panel de prompts de prueba de K-003 se ha sustituido por un indicador compacto y **Comprobar Codex**, junto al estado de API. El botón solo consulta instalación/login. No hay nuevas dependencias. Se documentan para K-008 las cuotas restantes por ventana y para K-011 la previsión de consumo con reserva, sin implementarlas aún.

## Contrato HTTP

Todas las rutas siguientes están bajo `/projects/{project_id}/conversations` y requieren host/origen local; los POST exigen JSON.

| Método | Ruta | Entrada / resultado |
| --- | --- | --- |
| GET | Raíz | Lista de chats del proyecto, de más reciente a más antiguo. |
| POST | Raíz | `{title, connector?, model?}` → chat creado; por defecto Simulado. |
| GET | `/{conversation_id}` | `{conversation, messages}` con historial ordenado. |
| POST | `/{conversation_id}/messages` | `{content, connector?, model?, confirm_subscription_use?}` → chat e historial actualizado. |

Cada consulta comprueba que el chat pertenece al proyecto de la ruta. Un ID de otro proyecto devuelve 404 y no invoca el conector. Los errores de validación no reflejan los campos del cuerpo. La confirmación de cuota debe ser un booleano real y se exige en cada envío a Codex, incluyendo el contexto previo.

`GET /connectors/{connector_id}/models` devuelve el catálogo visible; aplica las mismas comprobaciones de host/origen local y rechaza sesiones de API antes de consultarlo. El comando de catálogo en 0.165.x no admite `--ignore-user-config`: usa su configuración habitual, con proveedor oficial y login ChatGPT forzados y hooks/plugins deshabilitados, en un directorio aislado y con entorno sin claves. No inicia turnos ni herramientas. Tiene un límite propio de 15 segundos y 8 MiB por flujo, ya que el JSON incluye metadatos extensos; no se amplían los límites de las respuestas del chat. Los fallos del catálogo muestran un error controlado y permiten reintentar o conservar el modelo guardado/predeterminado.

No se mantiene una transacción abierta mientras responde el CLI. Un segundo envío simultáneo al mismo chat devuelve 409. Antes de guardar se comprueban de nuevo pertenencia e historial, para evitar sobrescribir otro turno o recrear un proyecto eliminado durante la consulta. Si falla SQLite, se revierte el turno entero y se devuelve un error controlado.

Se mantienen las protecciones de K-003: solo ChatGPT, rechazo de API, entorno sin claves heredadas, stdin sin shell, directorio aislado, CLI efímero, sandbox de solo lectura, herramientas deshabilitadas, tiempo/salida acotados y limpieza del grupo de procesos al cancelar. Los diagnósticos del CLI no llegan a la UI; se omiten formatos conocidos de credenciales en el texto almacenado o enviado como contexto. No se leen archivos de autenticación.

- Simulado por defecto; dos turnos ordenados y etiquetas HTML mostradas como texto. Se eligió `account-model` en el CLI ficticio, que recibió los cuatro mensajes previos del chat. Tras reiniciar, la UI recuperó el modelo y envió seis mensajes previos al continuar.
- Un fallo de red conservó el borrador y los seis mensajes anteriores. Cancelar abortó HTTP, terminó el PID del CLI ficticio y no guardó mensajes nuevos. No hay reintentos automáticos y la confirmación se restablece tras cada intento.
- Se crearon otro chat y otro proyecto: el primero conservó un historial separado y el segundo abrió una lista vacía. No se mezclaron contenidos al cambiar de chat/proyecto.
- Prueba real: primer mensaje «Recuerda la palabra FARO_LILA_731 para esta conversación. Responde únicamente MEMORIA_GUARDADA. No uses herramientas.». Codex devolvió `MEMORIA_GUARDADA`. Responde únicamente esa palabra, sin herramientas.», Codex devolvió `FARO_LILA_731`. Solo se hicieron esos dos envíos reales, con confirmación desde la UI y sesión de ChatGPT; sin APIs de pago.
- Sin errores JavaScript ni trazas del backend. Las peticiones de la página se limitaron a loopback. Revisión visual a 1100 × 850 y 640 × 640, sin desbordamiento horizontal.
- En Tauri se abrió el mismo proyecto/chat de la prueba ficticia, se recuperó el último turno y se actualizó el historial. Se cerraron y reiniciaron tanto API como escritorio, y se repitió correctamente. La entrada y el envío se verificaron en Chrome; la prueba nativa comprobó navegación, lectura, actualización y cierre.

El ajuste posterior del selector y panel se verificó con otra API/SQLite aisladas en el puerto 8011, utilizando la UI de desarrollo existente sin detener sus servicios:

## Límites y repetición manual

1. Iniciar API y escritorio como indica README. Crear un proyecto y un chat con nombre; completar dos turnos con Simulado.
2. Crear otro chat y otro proyecto; comprobar listas e historiales separados. Volver al primer chat.
3. Con Codex CLI compatible y login de ChatGPT, elegir Codex y un modelo del desplegable o su opción predeterminada. Confirmar cuota y enviar una palabra para recordar.
4. Cerrar escritorio y detener API. Reiniciar ambos, abrir el mismo proyecto/chat y preguntar por la palabra. Verificar contexto, orden, conector/modelo y confirmación nueva.
5. Para probar errores/cancelación sin consumo, usar los conectores/procesos ficticios de la suite. Comprobar que los turnos completados permanecen y que el borrador no se borra al fallar mientras se siga en el chat.
6. Si se pierde la conexión al recibir una respuesta, actualizar el historial antes de reenviar: el turno puede haberse confirmado justo antes de la desconexión. No hay reenvío automático ni recuperación de cuota ya consumida. Un borrador sin completar no persiste al salir del chat.

El contexto local no sincroniza las conversaciones ni la memoria nativa de Codex. El catálogo/acceso de modelos lo decide la cuenta y lo valida el CLI durante el envío; un rechazo se informa sin cambiar a una API. Al superar el contexto permitido se conserva el historial y se requiere otro chat. La autenticación por sesión del servicio local y el empaquetado siguen en K-012, antes de distribuir, como en K-003.
