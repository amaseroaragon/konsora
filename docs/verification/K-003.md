# K-003 — Proveedores de modelos

Fecha: 2026-10-29. Ubuntu 24.04, Python 3.12, Node 22 y escritorio Tauri.

**Estado: implementación verificada sin conexión; pendiente prueba real con OpenAI.** El usuario dispone de ChatGPT Plus. No se han solicitado ni utilizado credenciales reales ni se ha autorizado consumir saldo de API. La tarea continúa sin marcar hasta comprobar el prompt/respuesta real. No se ha iniciado K-004.

## Implementación

- Interfaz tipada `ModelProvider`, con información de disponibilidad y generación de texto. `MockProvider` da respuestas deterministas sin conexión ni credenciales. `OpenAIProvider` utiliza la API REST oficial de Responses.
- La configuración de OpenAI se lee al crear la aplicación desde `OPENAI_API_KEY` y `KONSORA_OPENAI_MODEL`. No hay modelo ni clave por defecto. Una configuración ausente o inválida deshabilita los envíos; el listado informa de ello sin consultar OpenAI.
- Se reutiliza HTTPX 0.28.1, ya presente en desarrollo, pasándolo a dependencia de ejecución para realizar solicitudes HTTPS asíncronas con timeouts. No se añaden SDKs ni otros paquetes.
- La UI permite seleccionar proveedor/modelo, introducir un prompt y limitar la salida (16–2048 tokens, 512 por defecto). El simulador está seleccionado inicialmente. El envío real requiere pulsar un botón que indica el consumo; no se envía al seleccionar un proveedor ni al actualizar su estado.
- Hay estados de carga y errores visibles, se impiden envíos duplicados mientras llega la respuesta y se conserva el prompt para reintentar. La respuesta se representa como texto, sin interpretar HTML. Esta prueba no crea conversaciones ni guarda prompts o respuestas en SQLite, archivos o almacenamiento del navegador.

## Contrato HTTP

| Método | Ruta | Entrada / salida |
| --- | --- | --- |
| GET | `/providers` | Lista de `{id, name, available, models, detail}`, sin credenciales. |
| POST | `/providers/{id}/generate` | `{model, prompt, max_output_tokens?}` → `{provider, model, text}`. |

El prompt debe tener entre 1 y 16000 caracteres tras recortar extremos; el modelo debe estar en la configuración del proveedor. No se aceptan campos adicionales ni URLs de destino. Los errores devuelven un `detail` controlado y, en errores del adaptador, un `code` estable.

| Situación | HTTP / código |
| --- | --- |
| Sin configuración | 503 / `not_configured` |
| Modelo no configurado | 422 / `invalid_model` |
| Credencial rechazada | 401 / `authentication` |
| Sin permiso | 403 / `permission` |
| Modelo remoto inaccesible | 422 / `model_unavailable` |
| Solicitud rechazada por OpenAI | 422 / `invalid_request` |
| Límite o saldo de API | 429 / `rate_limit` |
| Fallo de red | 502 / `network` |
| Timeout | 504 / `timeout` |
| Otro fallo remoto, redirección, respuesta inválida, incompleta o vacía | 502, con mensaje controlado |

## Credenciales y tráfico

- La clave solo reside en el entorno y la memoria del backend durante la sesión, protegida frente a representaciones accidentales mediante `SecretStr`. No hay endpoints para introducirla, consultarla ni devolverla. El README utiliza lectura oculta en terminal para evitar mostrarla o introducir su valor en el historial. No se leen archivos de autenticación de ChatGPT/Codex.
- El destino de autenticación es exclusivamente `https://api.openai.com/v1/responses`; se verifica TLS, se desactivan proxies del entorno y no se siguen redirecciones. `OPENAI_BASE_URL` no cambia el destino. Ninguna clave se envía a un dominio configurable, a la UI o al prompt del modelo.
- La petición lleva `store: false` y un límite de salida. Esto desactiva el almacenamiento de respuestas de Responses, sin prometer retención cero por parte de OpenAI. No hay herramientas, ejecución de código ni reintentos automáticos. Un timeout puede haber consumido tokens en el proveedor.
- Los errores remotos se convierten en mensajes fijos: no se devuelven cuerpos, cabeceras ni excepciones originales. También se omite el contenido de entrada en errores de validación. Si una respuesta de OpenAI incluyera la clave completa, se sustituye antes de devolverla.
- El backend de desarrollo sigue escuchando en loopback. Para las rutas de proveedores se comprueba el host local y se rechazan orígenes web ajenos a la UI, además de CORS; POST requiere JSON. Estas comprobaciones impiden solicitudes desde webs externas y hosts de DNS rebinding, pero no autentican otros procesos locales. El llavero del sistema, la autenticación por sesión y el ciclo de vida integrado siguen pendientes para distribuir en K-012.

Las 49 pruebas nuevas cubren el simulador y el flujo HTTP, configuración ausente/inválida, contrato REST de OpenAI con transporte simulado, redacción de la credencial ficticia, ausencia de la clave en respuestas y logs de nivel DEBUG, fallos 400/401/403/404/429/5xx, timeouts, fallos de red, respuestas inválidas/vacías/incompletas, rechazo de redirecciones y ausencia de reintentos, validación de entrada y protección frente a orígenes/hosts ajenos. La conexión de red real de HTTPX está bloqueada durante estos tests. Las 31 pruebas previas de proyectos/salud siguen pasando. Continúa un aviso de deprecación HTTPX/Starlette ya existente.

Se usó una instancia de API con base aislada en `.tools/k003-verification.sqlite3`, transporte HTTP simulado y una credencial expresamente ficticia. La verificación de Chrome recorrió UI → FastAPI → proveedor → respuesta → UI, sin peticiones de la página fuera de loopback:

- Proveedor simulado por defecto, prompt y respuesta correctos; el HTML recibido aparece como texto.
- En el adaptador OpenAI con transporte simulado: errores de autenticación, red, timeout y límite visibles, sin perder el prompt; recuperación al enviar de nuevo, bloqueo de controles durante la espera y ocultación de una credencial ficticia reflejada por el servidor simulado.
- Sin configuración: OpenAI informa del requisito y deshabilita el envío; el simulador sigue funcionando.
- Recargar vuelve al simulador y vacía el prompt/resultado; no hay persistencia de conversaciones en esta tarea.
- Revisión visual a 1100 × 820 y 640 × 600, sin desbordamientos horizontales ni errores JavaScript.
- Escritorio Ubuntu de producción: abre y muestra el panel, recibe el listado de proveedores de la API local, permite actualizarlo y cierra correctamente. La accesibilidad de WebKit no ofrece `EditableText` para esta pantalla; el envío con entrada de texto se comprobó en Chrome, no mediante automatización nativa.

## Repetir la prueba manual

1. Iniciar API e interfaz según el README, sin configurar credenciales.
2. Seleccionar Simulado, escribir un prompt, enviar y comprobar la respuesta. Recargar y comprobar que no se guardó.
3. Seleccionar OpenAI: comprobar el aviso de configuración y el botón de envío deshabilitado.
4. Para la prueba real pendiente, confirmar primero acceso y consumo de API con el usuario. Configurar clave mediante lectura oculta en la terminal del backend y el ID de un modelo de texto disponible para esa cuenta; reiniciar la API y actualizar proveedores.
5. Seleccionar OpenAI y enviar un prompt breve, por ejemplo «Responde solo: Hola». Comprobar la respuesta y el consumo en la cuenta. No registrar ni copiar la clave como evidencia. Si se agota el límite de salida, la UI muestra una respuesta incompleta; aumentar el límite conscientemente antes de reintentar.
6. Detener la API y quitar la variable de la terminal con `unset OPENAI_API_KEY`. La configuración no se conserva entre sesiones nuevas.
7. Solo después de una respuesta real satisfactoria, actualizar este informe y marcar K-003. Siguiente tarea: K-004.
